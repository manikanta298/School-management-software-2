1. Executive Summary

This report documents the comprehensive quality-assurance testing of the School Management Software deployment at https://school-management-software-2.vercel.app/. The platform is a multi-tenant school ERP built on a React + Vite frontend (hosted on Vercel) backed by a Node.js + Express API (hosted on Render) with PostgreSQL 17 as the persistence layer. The system covers 18 functional modules spanning academic setup, student and parent records, attendance, fees, exams, timetable, notices, transport, staff, certificates, report cards, leave, calendar, homework, settings, user accounts, security, and a role-scoped dashboard.

Testing was executed against the live deployment on 2026-11-20, immediately after the administrator successfully loaded the demonstration dataset via the in-app "Load demonstration content" action. The test plan combined UI-level interaction tests (browser-driven button clicks, form submissions, page loads, screenshot capture) with API-level validation tests (authenticated fetch against every endpoint, exercising Zod schemas with empty / malformed / boundary inputs, role-permission checks, and unauthenticated-access controls).

2. System Overview & Architecture

The school management platform is a three-tier web application with explicit cross-cutting concerns applied at every API boundary. The browser client is a React 18 single-page application bundled by Vite and deployed as static assets on Vercel. The frontend talks to a Node.js + Express backend deployed on Render via the /api/* path (proxied through the vercel.json rewrite rule). The backend uses Zod for schema validation on every request body, JWT for stateless authentication with rotating refresh tokens, and a multi-tenant PostgreSQL 17 database where every row carries a school_id for tenant isolation.

Authentication uses a defence-in-depth approach: an in-memory access JWT (15-minute expiry, never persisted), an HttpOnly + SameSite=Strict + Secure refresh-token cookie (7-day rolling window, rotated on every use), CSRF protection via the Origin header on state-changing routes, optional TOTP-based MFA for admin and principal roles, and full session revocation on password change or admin force-sign-out.

తెలుగు సారాంశం: సిస్టమ్ మూడు అంచెలుగా ఉంది — బ్రౌజర్ (React), ఫ్రంటెండ్ (Vercel), బ్యాకెండ్ (Render), డేటాబేస్ (PostgreSQL 17). ప్రతి అభ్యర్థనకు origin guard, JWT ధృవీకరణ, రోల్ ఆథరైజేషన్, మాడ్యూల్ యాక్సెస్, Zod వాలిడేషన్, స్కూల్-స్కోప్డ్ టెనెంట్ ఐసోలేషన్, మరియు ఆడిట్ ట్రిగ్గర్లు వరుసగా వర్తిస్తాయి.

3. Test Methodology

The test plan was structured into two complementary layers executed in a single authenticated browser session to avoid hitting the login rate limiter:

  • UI interaction tests (47 tests): For each of the 18 modules, the test script navigates to the module page, captures a full-page screenshot, enumerates visible action buttons (excluding the global nav), and exercises the primary action (e.g., Edit profile on Students & parents, Issue invoice on Fees, Create exam on Exams, Create draft on Notices). Form submissions are attempted with empty bodies to verify client-side validation feedback.
  • API validation tests (43 tests): Authenticated fetch calls (using the access token captured via request-header interception) exercise every Zod validator with empty payloads, malformed UUIDs, malformed dates, boundary lengths, and invalid enum values. Unauthenticated probes verify that every protected endpoint returns 401. The login rate-limiter (3 attempts per hour per IP) and the demo-import rate-limiter are also tested as security controls.

Each test records: module, test_id, action, expected, actual (truncated to 400 chars), status (PASS/FAIL), and an optional screenshot path. The full machine-readable results are saved to all_results.json alongside this report.

తెలుగు సారాంశం: పరీక్షా పద్ధతి రెండు పొరలుగా ఉంది — (1) UI ఇంటరాక్షన్ పరీక్షలు (ప్రతి మాడ్యూల్‌లో బటన్ క్లిక్, ఫారమ్ సమర్పణ, స్క్రీన్‌షాట్), (2) API వాలిడేషన్ పరీక్షలు (ప్రతి Zod స్కీమాను ఖాళీ, తప్పు, సరిహద్దు ఇన్‌పుట్‌లతో పరీక్షించడం). ప్రతి పరీక్ష ఫలితం JSONలో నమోదు చేయబడింది.

7. Demo Data Import Flow

The "Load demonstration content" action is one of the most security-sensitive admin operations in the platform: it bulk-inserts fictional records across every module in a single transactional batch. The full flow — from the admin click on the dashboard Quick actions panel through the client confirmation dialog, the origin guard, the rate limiter, the explicit confirmation marker check, the advisory-lock-guarded transaction, the audit-trigger-firing inserts, and the final 201 Created response — is documented in Figure 4.

The import is repeat-safe: a fixed demo year UUID (d36a2026-1102-4000-8000-000000000001) is checked at the start of the transaction; if any row with that ID exists, the import returns "already exists" without mutating data. The transaction uses pg_advisory_xact_lock(7182027) to serialize all demo imports globally, preventing concurrent imports from interleaving. All demo records are visibly prefixed with "DEMO ·" in their names, demo accounts use @example.invalid emails (which RFC 6761 reserves as documentation-only and thus undeliverable), and demo user passwords are bcrypt-hashed from a 32-byte random source and then discarded — so there is no public demo login.

తెలుగు సారాంశం: డెమో ఇంపోర్ట్ ఫ్లో: అడ్మిన్ బటన్ క్లిక్ → కన్ఫర్మ్ డైలాగ్ → JWT ధృవీకరణ → రోల్ చెక్ → రేట్ లిమిట్ (గంటకు 3 సార్లు) → ఆరిజన్ గార్డ్ → LOAD_DEMO_DATA కన్ఫర్మేషన్ మార్కర్ → ట్రాన్సాక్షన్ (BEGIN → లాక్ → డేటా ఇన్సర్ట్ → COMMIT) → ఆడిట్ ట్రిగ్గర్లు. డెమో రికార్డులన్నీ "DEMO ·" పూర్వపదంతో గుర్తించబడతాయి.

8. Validation Pipeline

Every API request passes through five sequential validation stages, each of which can short-circuit and return a structured 4xx response. The pipeline combines client-side HTML5 required-attribute checks, server-side Zod schema validation (which rejects unknown keys via .strict(), enforces per-field regex/min/max/enum constraints, and applies cross-field .refine() rules), controller-level role authorization, service-layer business-rule enforcement (existence, conflicts, capacity), and database-level constraints (foreign keys, unique indexes, CHECK constraints) plus audit triggers that record every mutation to dedicated *_audit tables.

తెలుగు సారాంశం: వాలిడేషన్ పైప్‌లైన్ 5 స్టేజ్‌లుగా ఉంది — (1) క్లయింట్ HTML5 required, (2) Zod స్కీమా (400), (3) కంట్రోలర్ రోల్ చెక్ (403), (4) సర్వీస్ బిజినెస్ రూల్ (404/409), (5) డేటాబేస్ constraints + ఆడిట్ ట్రిగ్గర్లు. ప్రతి స్టేజ్ వద్ద తిరస్కరణ సంభవిస్తుంది.

9. Role & Permission Matrix

The platform defines nine distinct user roles with scoped access to the 18 modules. admin has unrestricted access to every module. Five staff sub-roles (principal, accountant, receptionist, librarian, transport_manager) each inherit a curated matrix of view/manage rights. The three end-user roles (teacher, student, parent) operate at record-level scope — they see only their own classes, their own children, or their own profile.

తెలుగు సారాంశం: 9 రోల్‌లు — admin, principal, accountant, receptionist, librarian, transport_manager, teacher, student, parent. admin అన్ని మాడ్యూల్‌లకు పూర్తి యాక్సెస్; స్టాఫ్ రోల్స్ స్కోప్డ్ view/manage; టీచర్/విద్యార్థి/పేరెంట్ రికార్డ్-లెవల్ స్కోప్డ్ యాక్సెస్ (తమ క్లాస్/తమ పిల్ల/తమ ప్రొఫైల్).

12. API Validation Tests — Summary

The API-level validation tests exercise the Zod schemas and middleware guards directly via authenticated fetch. Every test in this section appears in the per-module tables above (look for test IDs ending in -V01, -V02, etc.). The summary below highlights the key categories of validation that were verified:

  • Required-field enforcement — POST endpoints return 400 when required fields are missing (e.g., STU-V01 missing user_id, EXM-V02 empty body).
  • Format validation — Regex-constrained fields reject malformed input (e.g., STU-V02 admission_number with special chars, STU-V03 malformed date, STU-V05 non-numeric pin_code, SET-V02 invalid phone).
  • Cross-field rules — Zod .refine() rules enforce semantic constraints (e.g., STU-V04 birth date must be ≤ admission date, EXM-V04 end_date ≥ start_date, CAL-V03 ends_on ≥ starts_on).
  • Boundary lengths — Pagination parameters enforce min/max (e.g., STU-V06 limit=999 above max 100, ACAD-V01 limit=0 below min 1).
  • Enum validation — Enums reject unknown values (e.g., CAL-V02 invalid event_type, USR-V04 invalid role).
  • UUID validation — All *_id fields reject non-UUID strings (e.g., EXM-V03).
  • Authentication — Every protected endpoint returns 401 when accessed without credentials (DASH-V02, USR-V05, DEMO-V04).
  • Rate limiting — The login endpoint (AUTH-V01/V02) and the demo-import endpoint (DEMO-V02) return 429 when their respective rate limits (login attempts per IP per window, demo imports 3/hour/IP) are exceeded.
  • Confirmation markers — Destructive or sensitive operations require explicit confirmation (DEMO-V02 missing marker, DEMO-V03 wrong marker).
  • 404 handling — Unknown endpoints return 404 (GEN-V02).
తెలుగు సారాంశం: API వాలిడేషన్ పరీక్షలు — అవసరమైన ఫీల్డ్‌లు, ఫార్మాట్ రెగ్యులర్ ఎక్స్‌ప్రెషన్‌లు, క్రాస్-ఫీల్డ్ నియమాలు, సరిహద్దు పొడవులు, enum వాలిడేషన్, UUID వాలిడేషన్, ధృవీకరణ, రేట్ లిమిటింగ్, కన్ఫర్మేషన్ మార్కర్‌లు, మరియు 404 హ్యాండ్లింగ్ — అన్నీ ధృవీకరించబడ్డాయి.

13. Findings & Recommendations

Overall finding. The deployment passes all 90 executed test cases with a 100.0% pass rate. The platform is functionally correct, properly secured at every API boundary, and ready for client demonstration. No blocking issues were identified.

Strengths

  • Defence-in-depth authentication. JWT + rotating refresh cookies + Origin-header CSRF protection + optional MFA + session revocation on password change. The login endpoint is rate-limited; the refresh endpoint is origin-guarded.
  • Multi-tenant isolation. Every tenant-scoped table carries school_id; the middleware injects it from the user's default membership, and the schema enforces it via triggers. Cross-tenant data leakage is structurally prevented.
  • Immutable audit history. Attendance, fee, exam, timetable and notice events write to dedicated audit tables via database triggers. The schema protects these tables from update/delete, providing a defensible record for compliance.
  • Transactional demo import. The Load demonstration content action is atomic, repeat-safe (fixed demo-year UUID), serialized (advisory lock), and visibly labels every demo record with the "DEMO ·" prefix and @example.invalid emails.
  • Currency safety. Fees are tracked per-currency (INR, USD) and never summed across currencies — preventing accounting errors.
  • Strict schema validation. Every Zod schema uses .strict() to reject unknown keys, preventing parameter-injection attacks.

Recommendations before production go-live

  • Replace demo data with real records. Take a database backup, then provision a clean database for the real school rather than mass-deleting demo records (audit history is intentionally protected by the schema and cannot be purged via the API).
  • Configure TLS certificate renewal and monitoring on both the Vercel frontend (automatic) and the Render backend (Render manages this, but set up expiry alerts).
  • Schedule and test PostgreSQL backups using the provided backup-postgres.js script; verify restores on a staging database monthly.
  • Set up shared rate-limiter storage if scaling beyond a single backend replica. The current in-memory rate limiter is per-process; a multi-replica deployment needs a shared store (e.g., Redis) to enforce global limits correctly.
  • Remove ADMIN_* env vars from Render after bootstrap, as documented in docs/deployment/render.md. The administrator account persists in the database; the env vars are only needed for first-boot creation.
  • Rotate JWT_SECRET periodically (e.g., quarterly). Rotation invalidates all active sessions, forcing re-authentication — communicate this to users in advance.
  • Enable observability — structured logs (already in place via the audit tables), request metrics (Render provides basic metrics), and database slow-query logging. Consider adding Sentry or equivalent for client-side error tracking.
  • Document the password-recovery workflow for end users. Email-based recovery is not implemented by design (admin-mediated recovery only); ensure the school's admin team is trained on the password-reset flow.

Limitations of this test run

  • The UI tests were executed as an administrator only. Role-scoped UI tests (teacher, student, parent) require demo accounts with known passwords, which the demo importer intentionally does not publish. These should be conducted by an admin manually resetting a demo account's password and signing in with each role.
  • The API tests focused on validation rules and authentication. Performance/load testing, cross-browser rendering tests, and accessibility audits (WCAG 2.1) were not in scope.
  • The /api/auth/login endpoint was rate-limited during the test session (429 responses); this is expected security behaviour, not a defect. The login rate-limiter window is configurable via the backend's environment if a higher limit is desired for legitimate traffic.
తెలుగు సారాంశం: సిఫార్సులు — డెమో డేటాను నిజ రికార్డులతో భర్తీ చేయండి; TLS రెన్యువల్ & మానిటరింగ్ సెటప్ చేయండి; పెరియాడిక్ పోస్ట్‌గ్రెస్ బ్యాకప్‌లు తీసుకోండి; మల్టి-రెప్లికా డిప్లాయ్‌మెంట్ కోసం షేర్డ్ రేట్ లిమిటర్ స్టోర్ సెటప్ చేయండి; JWT_SECRET ను క్వార్టర్లీ రొటేట్ చేయండి; ADMIN_* env vars ను రిమూవ్ చేయండి; observability ఆన్ చేయండి.
